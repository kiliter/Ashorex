# ADR-0026：心跳在线判定与催办策略只在服务端配置

- 状态：提议（待人工批准）
- 日期：2026-09-07
- 相关：取代 ADR-0012（管理端验活间隔）；配合 ADR-0025、ADR-0028

## 背景

V2 取消了进度验活，但监督仍需要一个「用户是不是在摆」的判据。用户要求：

- App 固定周期上报心跳，服务端维护在线状态；
- 服务端定期扫描每日待办完成情况，超过可调阈值且无任何操作时发通知；
- 通知渠道需要抽象，当前是 Server 酱 + 客户端全屏弹框，全屏弹框必须确认且必须填写原因；
- 阈值与渠道配置**不放在 App 内**，只在服务端 Web 管理后台维护。

## 决策

### 心跳与在线

- App 每 `heartbeatIntervalSeconds`（默认 60 秒）调用 `POST /api/v1/heartbeat`，携带 `appState`、`clientVersion`、本地待同步事件数；服务端在响应中下发实际间隔与待回应催办 ID。
- 只维护 `user_presence` 单行当前态，**不落心跳明细历史表**，避免产生大量无价值行。
- 在线判定：`now - last_heartbeat_at <= presence_grace_seconds`（默认 150 秒，即心跳间隔 × 2.5）。
- 引入「有效操作」概念：进度上报、完成、勾选、附件上传、创建 / 删除 Todo、催办回应。**心跳不是有效操作**，否则挂着 App 就永远不会被判定为空闲。空闲时长 = `now - last_effective_action_at`。

### 催办领域对象

- `Nag` 是独立聚合，含触发条件快照（`idleMinutes`、`pendingCount`）、状态机 `PENDING → DELIVERED → RESPONDED | EXPIRED`、回应原因。
- `NagDelivery` 记录每次投递（渠道、结果），同一个 `Nag` 可以有多条投递流水。
- 渠道抽象为 `NagChannel` 接口，V2 两个实现：`FullscreenChannel`（提交后 SSE 通知，心跳响应兜底，可切回纯心跳）、`ServerChanChannel`（HTTP 推送，带超时）。
- 降级规则：在线 → 全屏；离线 → Server 酱；全屏投递后超过 `fullscreenTimeoutMinutes` 未回应 → 追加 Server 酱投递。
- 幂等键 `(user_id, local_date, threshold_level) WHERE trigger='AUTO'`，同一天同一档只会生成一次。手动与督学催办不参与幂等键，但计入每日上限。

### 配置归属

- `nag_policies` 有一行 `scope=GLOBAL`，可有多行 `scope=USER` 覆盖。
- 覆盖只影响阈值与渠道类字段；`scanIntervalMinutes`、`presenceGraceSeconds`、`heartbeatIntervalSeconds` 只取全局值，避免每用户不同扫描周期带来的调度复杂度。
- App 端**没有任何**催办配置入口，只通过 `GET /api/v1/me` 只读拉取当前生效策略用于展示。

### 客户端义务

- 收到 `pendingNagId` 必须拉起全屏弹框：不可点击外部关闭、不可返回、不可切 Tab，必须选择或填写原因（默认最少 5 字）才能提交。
- 心跳失败不影响本地播放与计时，只在首页显示离线条与待同步条数。

### 投递流水可观测性

只记录「催办发出去了没有」不够：管理员真正要判断的是「没发出去是因为什么，我该做什么」。因此对投递流水追加以下约束。

- 每次投递尝试都写一行 `nag_deliveries`，**无论成败**；渠道未注册或不可用时也写，不允许静默 return。
- `nag_deliveries.detail` 是管理员可直接阅读的中文短语，不含 SendKey、目标地址、第三方响应正文与堆栈。渠道不可用时原因由渠道自述，接口方法为 `NagChannel.unavailableReason()`（默认实现返回「渠道不可用」）。Server 酱区分「Server 酱未配置 SendKey」与「Server 酱催办推送已关闭」，因为前者要去填配置、后者要去打开开关，处置动作完全不同；渠道根本没注册时写「渠道未注册」。
- `GET /admin/api/nags` 返回 `deliveryAttempts`：以 `nagId` 为键、按 `created_at` 升序的尝试数组（`channel` / `status` / `detail` / `createdAt`）。后台催办记录页据此把「还没轮到扫描」与「两个渠道都打不通」分开显示。
- **不为投递失败新增 `Nag` 状态机终态。** 状态机保持 `PENDING → DELIVERED → RESPONDED | EXPIRED`。失败是投递层的事实，不是催办本身的生命周期节点；一条催办的两个渠道可能一失败一成功，把失败提升成终态会丢掉这个区别，也会让幂等键与每日上限的语义跟着变。代价是「按 `nags.status` 聚合」与「按投递尝试判定」两处口径必然不等，后台必须在状态分布卡的「待投递」下标注其中有多少条已尝试且全部失败，把差异解释清楚，而不是靠改数据模型抹平。
- `app.serverchan.base-url` 是推送基址配置项，默认值即 Server 酱生产地址。提取它只为让协议测试指向本地假服务，**不是面向管理员的运行配置**，因此不进管理后台「运行配置」页，也不随任何 API 下发。

## 后果

正面：

- 用户侧零配置，策略集中在一处，避免「App 改了一个值、服务端还是老阈值」的不一致。
- 不落心跳历史，SQLite 体积可控，符合「不要垃圾数据」的要求。
- 渠道抽象让后续接入其他推送（邮件、企业微信）只需新增实现类。

负面与代价：

- 用户不能自行调节被打扰的强度，只能请管理员改。对单人自托管场景可接受。
- 在线判定依赖客户端心跳，App 被系统杀死后会被判为离线，此时只能走 Server 酱。这是可接受的行为，不引入推送证书；前台 SSE 见下方已批准变更。
- 免打扰时段内只累计不投递，可能出现「早上一次性看到昨晚的未完成」，属预期。
- 投递失败不进状态机导致后台两处状态口径天然不等，只能靠文案解释，不能靠数据抹平。这是刻意选择：宁可页面多一行说明，也不要为展示方便污染领域状态机。

## 替代方案

1. **App 内提供阈值设置**。否决：用户明确要求放在服务端 WebUI。
2. **保存心跳明细以便审计**。否决：价值低、体积大，且 `user_presence` + 催办记录已足够复盘。
3. **把心跳当作有效操作**。否决：会让「开着 App 不学」永远不触发催办，违背催办目的。
4. **用长连接（WebSocket）替代心跳轮询**。否决：单实例小规模场景不值得引入连接管理与重连复杂度。
5. **给 `Nag` 加 `FAILED` 终态，让后台状态分布与流水行天然一致**。否决：失败属于投递层而非催办生命周期，一条催办可能一个渠道失败、另一个成功，加终态会丢掉这个区别，并连带改变幂等键与每日上限的语义。改为在分布卡标注失败条数。

## 2026-09-08 已批准变更：催办通知传输模式

- 默认 `SSE`，后台「催办策略」提供全局切换为 `HEARTBEAT`（原心跳轮询），不允许按用户覆盖。
- 新增 `GET /api/v1/nags/events`，Bearer 认证，仅订阅当前用户；`ready` 触发补查，`nag` 的 data 为催办 ID，保活注释不更新在线或有效操作。
- 催办事务成功提交后通知，数据库仍是唯一事实来源；连接断开、事件重复或丢失都通过待回应查询兜底，不新增消息历史表。
- 连接最长 60 秒后重新认证，每 15 秒保活；前台断线按 1～30 秒退避重连，回前台立即重连补查，退出时释放。
- 心跳始终保留，返回 `nagTransportMode`；客户端下一次心跳应用后台模式切换（默认最长 60 秒）。旧服务端缺少字段时按 HEARTBEAT 兼容。
- 已投递依旧表示通知已受理，不表示用户已经看到。Server 酱降级和全屏回应规则保持不变。
- 验收要求：提交后通知/回滚不通知、用户隔离、配置切换、SSE 分帧、重连与取消、重复通知仅显示一个弹框；追加迁移，不修改 V001。

### 弱网与资源回收细则

- 客户端连续 45 秒收不到数据即关闭异常流；收到保活注释会续期，但不会产生催办或有效操作。
- 建连使用现有 Bearer 刷新流程；认证彻底失效仍退出登录，普通断网不清除凭据。
- 网络写入在虚拟线程中执行，每连接最多一个在途发送；慢连接不积压内存消息，未回应记录由心跳补查。
- 每用户最多 5 条连接，超额关闭最旧连接；断开、超时和服务关闭时清理连接。
- SSE 与心跳重复通知共用全屏展示锁；回应后继续补查下一条，不在页面展示期间丢掉后续催办。
- 反向代理应允许流式响应，不缓存 `/api/v1/nags/events`，读取超时应大于 60 秒。服务端返回 `X-Accel-Buffering: no` 与 `Cache-Control: no-cache, no-transform`；外部代理链路仍需部署环境实测。
