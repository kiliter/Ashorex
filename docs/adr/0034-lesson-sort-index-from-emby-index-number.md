# ADR-0034：课时序号以 Emby `IndexNumber` 为权威来源，禁止用列表位置推导

- 状态：提议（待人工批准）
- 日期：2026-09-08
- 相关：修正 ADR-0027（Emby 元数据为唯一分类来源）与 ADR-0030 中 `sortIndex` 的取值语义；影响 Spec 第 12 章

## 背景

`learning_resources.sort_index` 决定学习端课程详情页里课时的展示顺序，也决定「第几讲」这个用户心智里的稳定编号。

V2 首轮实现把它写成了远端返回列表的位置：

```java
// EmbyClient.listChildren（修复前）
uniqueItems.putIfAbsent(id, mediaItemFromNode(item, uniqueItems.size() + 1));
```

请求 Emby `/Users/{userId}/Items` 时，`Fields` 只声明了 `RunTimeTicks,Path,SortName`，**从未请求 `IndexNumber`**，因此序号完全由「这一项在本次分页结果里排第几」决定。

用假 Emby 实测取证（8 讲的 CPA 课程，远端下架第 05 讲后重新同步）：

```text
sort_index | available | title
        4  |     1     | 第04讲 长期股权投资权益法核算
        5  |     0     | 第05讲 收入确认五步法模型详解   <- 下架，序号冻结在 5
        5  |     1     | 第06讲 金融资产分类与后续计量   <- 撞号
        6  |     1     | 第07讲 所得税递延资产与负债
        7  |     1     | 第08讲 合并财务报表编制入门     <- 从 8 前移到 7
```

两个后果都属于数据正确性问题，违反 AGENTS.md 决策优先级第 1 条：

1. **整体前移**：远端删一集，其后每一集的「第几讲」都变。用户昨天看的「第 07 讲」今天变成「第 06 讲」，而 Todo 与统计里留下的仍是旧标题，人对不上账。
2. **撞号**：下架课时保留旧序号，前移后的在线课时占用同一个 `sort_index`。列表 `ORDER BY sort_index, title` 的相对顺序退化为按标题排序，同号两项的先后不再稳定。

这与假 Emby 无关。真实 Emby 的 `/Items` 结果同样会因为条目增删而改变位置，只要用位置推导就必然复现。

## 决策

### 序号只认远端 `IndexNumber`

1. `EmbyClient.requestPage` 的 `Fields` 显式加入 `IndexNumber`；`readParent`（Movie 直接作为课程来源的场景）同样加入。按仓库既有约定，凡业务依赖的字段一律显式声明，不依赖不同 Emby 版本的默认字段集。
2. `mediaItemFromNode` 只读远端 `IndexNumber`。缺失、为 `null` 或非正数时置 `0`，表示「未知序号」，不再由调用点塞入位置。
3. 新增 `EmbyClient.resolveIndexNumbers`，在整份远端快照收齐后一次性定稿序号：
   - 有 `IndexNumber` 的条目直接采用。Emby 的 Episode `IndexNumber` 就是集号，是远端稳定编号，不随同批次里其他条目的增删变化。
   - 缺失 `IndexNumber` 的条目（常见于 `Movie` 与散装 `Video`）才回退到远端列表位置，并统一排在**已知集号最大值之后**，保证同一课程内不与集号撞号。
   - 全部条目都没有 `IndexNumber` 时最大值为 0，退化为 1、2、3……与修复前行为一致，纯视频文件夹类课程的既有序号不受影响。

`SortBy` 仍为 `SortName`，不改分页排序。分页排序只影响「缺失集号」时的回退顺序，改动它会让存量文件夹型课程的序号无谓漂移。

### 下架课时的序号语义

远端消失的课时**只标记 `available=0`，`sort_index` 冻结在最后一次同步到的值**，不清零、不重排、不腾挪。

这个语义在 `IndexNumber` 方案下是自洽的：冻结值等于该课时自己的集号，不会被任何在线课时占用，因此不会撞号。远端重新上架时按 `external_ref` 原位匹配，序号随之刷新。语义已写入 `CourseSyncService.applyPlan` 的注释。

### 对已入库错误数据的纠正

不需要数据迁移，也不新增 `V002`。

`CourseSyncService.applyPlan` 对每个原位匹配项都调用 `updateResourceSyncedFields(..., remote.sortIndex(), ...)`，即 `sort_index` 每次同步都被远端值整列覆盖。因此历史上被位置逻辑写错的序号会在**下一次同步时自动纠正**，纠正走原位更新：

- `learning_resources.id` 不变——硬约束「本地资源 ID 永不重建」不被触碰；
- `external_ref` 不变，不产生多余的 `resource_source_mappings` 审计行；
- 进度、Todo 引用、专注时长与统计聚合全部按 `id` 关联，不受影响。

`sort_index` 上没有唯一索引（`V001` 只有 `(course_id, status, available, sort_index, id)` 的普通索引），因此存量撞号数据在纠正过程中不会触发约束冲突。

### 开发工具同步

`scripts/fake_emby.py` 的 Episode 节点补上 `IndexNumber` 与 `ParentIndexNumber`，与真实 Emby 对齐。否则假 Emby 会持续走回退分支，掩盖这类回归。

## 后果

正面：

- 「第几讲」成为远端稳定编号，远端增删课时不再改变其余课时的编号。
- 同一课程内序号不再撞号，列表顺序确定。
- 存量错误数据在下一次同步自动收敛，无需迁移脚本与停机窗口。
- 假 Emby 更接近真实 Emby，此类回归可在本机复现。

负面与代价：

- 序号不再连续。远端下架第 05 讲后，学习端会看到 1、2、3、4、6、7、8。这是有意的：编号稳定比编号连续重要，用户按「第几讲」记住的内容不能被平移。列表页仍按 `sort_index` 升序展示，不显示缺口占位。
- 依赖 Emby 元数据质量。若管理员在 Emby 里把两集标成同一个 `IndexNumber`，本地就会撞号。这与 ADR-0027「筛选维度主数据不由本项目维护」的立场一致：元数据错误在 Emby 侧修正，本项目不做兜底重排，否则又会引入「本地编号与远端不一致」的第二套真相。
- 混合库（部分条目有集号、部分没有）里，无集号条目排在集号之后，展示顺序可能与管理员在 Emby 里看到的不同。这类库本身没有权威编号，接受该退化。

## 替代方案

1. **每次同步按远端列表位置整体重排 1..N**。否决：这正是 bug 的根因加强版。它消除了撞号，但把「编号会莫名平移」变成常态，用户记忆的「第几讲」随远端增删漂移。
2. **序号一次性写入，之后永不更新**。否决：首次同步时若远端顺序异常就永久错误，且无法修复存量已错数据；也无法反映管理员在 Emby 里的正常重排。
3. **本地维护课时顺序，提供后台拖拽排序**。否决：与 ADR-0027 冲突——课程结构主数据来自 Emby，本项目不提供编辑入口。同时会产生本地顺序与远端顺序两套真相和随之而来的冲突合并逻辑。
4. **写 `V002` 迁移，按标题里的「第NN讲」正则回填 sort_index**。否决：标题格式是内容方约定，不是数据契约；CET6 那类「Section A 长对话精讲」根本没有编号可提取。同步覆盖已经能纠正数据，迁移是多余风险。
5. **给 `(course_id, sort_index)` 加唯一索引兜底**。否决：唯一索引会把「远端元数据撞号」变成同步整体失败，牺牲可用性去换一个本项目无权修复的数据问题。撞号已由 `IndexNumber` 语义在正常路径消除。
6. **改用 `SortBy=ParentIndexNumber,IndexNumber` 让远端直接排好序**。否决：只解决排序，不解决编号；缺失集号的条目仍需回退规则。且会改变存量文件夹型课程的既有序号。
