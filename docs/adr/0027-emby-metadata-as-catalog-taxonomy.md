# ADR-0027：课程分类与讲师维度全部来自 Emby 元数据，本地只存只读投影

- 状态：提议（待人工批准）
- 日期：2026-09-07
- 相关：延续 ADR-0003、ADR-0015、ADR-0016；配合 ADR-0030

## 背景

V2 的「学习」Tab 需要按科目、讲师、课程阶段等维度浏览课程库。最初的设计草案是在上岸内部建立 `course_categories`、`instructors`、课程阶段等主数据表，由管理员在后台维护并绑定课程。

用户否决了这个方向，要求：分类、讲师这些维度直接绑定 Emby 的**流派（Genres）、标签（Tags）、人物（People）**，上岸内部不维护这些数据的人工维护结构，只在导入 Emby 课程时加载；后续还要能与本地文件 / NFO 保持一致。

## 决策

- 上岸**不建立**分类、讲师、阶段的主数据表，也不提供任何人工编辑入口。
- 元数据映射固定为：`Genres → 流派（科目）`、`Tags → 标签（阶段 / 年份等自由标签）`、`People → 人物（讲师）`、`ProductionYear → 年份`、`Name / Overview → 标题 / 简介`。
- 本地保存三张**只读投影表**：`course_genres(course_id, genre, sort_order)`、`course_tags(course_id, tag, sort_order)`、`course_people(course_id, person_name, role, sort_order)`。它们由同步任务**整表重写**（先删后插），管理员不可编辑。
- 移动端筛选与分组维度全部由这三张表 `DISTINCT` 聚合得出（`GET /api/v1/catalog/facets`），不存在维度实体的 ID。
- 课程本地唯一可编辑字段是 `sort_order` 与启用 / 归档状态。名称、流派、标签、人物、年份、简介一律标注「来自 Emby · 只读」，需要修改请回 Emby 改后重新同步。
- 元数据变更（改名、重打标签、增删人物）**只重写投影，不触发任何数据迁移**；统计与进度按 `courses.id` 与 `learning_resources.id` 聚合，因此历史结果不受影响。

## 为什么仍然落库

用户的要求是「不要在项目里维护任何数据结构」，指的是不做人工维护的主数据 CRUD。完全不落库（每次筛选实时查 Emby）会带来三个后果：

1. 学习 Tab 与数据 Tab 的筛选、分组、排行全部依赖 Emby 在线，Emby 不可用时课程库不可浏览。
2. 「按人物聚合我的学习时长」需要把本地时长与远端元数据在应用层 join，每次都要全量拉取。
3. 无法建立索引，小规模下虽可行，但代码复杂度反而更高。

因此采用**只读快照投影**：数据来源仍是 Emby 单一事实源，本地只是可查询缓存，无人工写入路径，不构成「自建主数据」。该取舍已向用户说明并获得「可自行发挥、不要过度设计」的授权。

## 后果

正面：

- 维度维护成本为零，管理员只在 Emby 里整理媒体库即可。
- 离线可筛选、可统计、可建索引。
- 与后续本地文件 / NFO 来源统一（见 ADR-0030），因为 NFO 字段名与 Emby 一致。

负面与代价：

- 元数据质量完全取决于 Emby 媒体库的整理质量；流派命名不规范会直接体现在 App 上。
- 无法在上岸内做「同义维度合并」（例如「注会」与「CPA」）。若将来需要，只能新增映射规则，而不是编辑主数据。
- 每次同步都整表重写投影，会产生短时写入放大。在小规模下可忽略。

## 替代方案

1. **建立本地分类 / 讲师主表并人工绑定**。否决：用户明确否决，且维护成本高。
2. **完全不落库，实时查询 Emby**。否决：牺牲离线可用性与统计能力，代码更复杂。
3. **落库但允许管理员覆盖 Emby 值**。否决：会产生「本地值与远端值冲突」的第三种状态，增加同步分支，属过度设计。
